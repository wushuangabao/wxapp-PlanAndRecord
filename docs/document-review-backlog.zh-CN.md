## 代码与产品一致性待复核

以下事项均为审查发现，每行状态以优先级列和末尾确认记录为准。记录这些事项不表示已经修改产品基线；未写明已确认方案的事项也不表示已经选定修复方案。

| 优先级 | 议题 | 现状与待复核事项 |
| --- | --- | --- |
| P2（延期） | 重复规则“此项及后续”的修订语义 | 编辑弹层允许输入标题，但提交“此项及后续”修订时未传递标题，用户输入不会生效。若先修改较晚实例，再回头修改较早实例，当前实现还可能留下生效区间重叠的未来修订，使不同投影入口选择不同结果。后续需统一确认标题是否属于修订字段，以及“从较早实例修改此项及后续”是否替换其后的既有修订；同时补齐修订链互斥校验、JSON 校验和回归测试。2026-08-03 已确认本轮不修，仅保留本项等待以后处理。 |
| P2（延期） | 删除固定日程种子计划块后同一实例重新出现 | 页面允许删除带 `repeatRuleId` 的实体种子计划块并提示“计划块已删除”，但应用服务只删除 `CalendarEvent`，既不删除对应重复规则，也不为该逻辑实例写入 `skip`；下一次投影会立即在同一时间重新生成虚拟实例。后续需明确该入口表示“仅跳过本次”还是“删除整个固定日程”，并保证实体删除、例外写入、关联清理和失败回滚具有一致的原子语义。2026-08-03 已确认本轮不修，仅保留本项等待以后处理。 |
| P2（延期） | 统一详情页与日志来源追溯尚未落地 | 产品基线要求点击计划块或日志进入统一详情，并能追溯日志来自计时器、固定日程、OCR、文本导入或手工补录；当前日历和“最近记录”只提供各自的零散展示与操作，没有统一详情入口，也没有展示原始 `source`。后续建议由应用服务提供统一详情读模型，增加非 Tab 详情页，并统一展示日志状态、不可编辑的原始来源、当前有效关联与明确标注的历史快照；重复规则投影仍按计划实例展示，不得伪装成持久化候选日志。2026-08-03 已确认本轮不修，仅保留本项等待以后处理。 |
| P2（延期） | 例行临时导出清理失败后没有自动重试 | 导出完成后的异步清理和进入用户页时的历史临时文件清理都只尝试一次；非“文件不存在”错误只记录日志，与此前确认的“后台自动重试一次”不一致。后续建议为页面级 best-effort 清理建立统一执行器，每轮最多执行两次；文件不存在视为成功，第二次仍失败时只记录一条脱敏警告并留待下次进入用户页重新清理，单个文件失败不得阻断其他明确归属文件。严格“清空数据”的失败中止与原子性要求不属于本项，必须保持不变。2026-08-03 已确认本轮不修，仅保留本项等待以后处理。 |
| P1（待确认） | 单键布局撞微信 1MB 上限 | 整个资料库序列化进唯一的 `plan-and-record.database`。按当前字段集实测，单条 `TimeLog` 约 475 到 620 字节，2000 条即占满 1MB（实测 1029 KB）；目标用户每年产生约 1800 到 5500 条，正常使用一年内到顶。到顶后每次 `wx.setStorageSync` 抛错并统一包成 `WRITE_FAILED`，文案是“请重试”，而重试同一份超限数据永远不会成功；唯一出口是删记录，界面没有任何提示。代码全程无配额感知，`WxStorageAdapter.has()` 已在调 `wx.getStorageInfoSync()` 却丢弃了 `currentSize` 与 `limitSize`；10MB 总量配额也未被利用。产品设计原先完全没有容量维度，现已在 [product-design.zh-CN.md](./product-design.zh-CN.md) 5.4.5 定为正式方案。2026-08-06 已确认路线：首版保留单键布局不做分片，补齐用量可见、阈值预警和到量出口（导出 JSON，以及只预留界面与 `SyncPort` 调用的上云入口）；时间日志分片与云端同步排入第二阶段，以可用的结构迁移框架为前提。预警阈值同日确认取单 key 上限的 90%。本行保留至首版三项补齐并验证为止。 |
| P1（待确认） | `migrate` 没有升级路径，升级前快照键从未写入 | `LocalRepository.migrate` 只处理 `schemaVersion` 恰好等于当前版本的情况，低于当前版本的一律抛 `DATA_VERSION_UNSUPPORTED`。函数名为 `migrate` 但不迁移任何数据，因此一旦发布 `schemaVersion = 2`，全部存量用户冷启动即被路由到恢复页，只能清空重建或导入未必存在的备份。配套地，`BACKUP_KEY`（`plan-and-record.database.pre-migration`）在生产代码中只被读取和删除，从未被写入，产品基线 5.4 要求的“为结构迁移保留升级前快照”属于完全未实现。2026-08-06 已确认 [product-design.zh-CN.md](./product-design.zh-CN.md) 5.4.4 为正式方案，其中规定迁移必须是可执行的逐级升级路径、升级前快照的写入与删除时点，以及单键平台上“原子提交”的准确含义；本行保留至代码按该节实现为止。修复须与下一条的空值语义一并处理。 |
| P1（待确认） | 全量写放大与计时草稿逐字符落库 | 一次 `transaction` 会做 6 次 `JSON.parse(JSON.stringify())` 深拷贝、一次完整 `storage.get` 反序列化、一次完整序列化写入，外加整库 `validateJsonSnapshot`。其中 `writeTransaction` 里的 `oldMain = this.storage.get(STORAGE_KEY)` 是纯冗余，同一份数据已在 `this.cache`。桌面 Node 实测单次事务耗时：500 条日志 15.7ms，2000 条 57.1ms，5000 条 143.8ms，真机更慢。而计时页 `onNoteInput` 无防抖，每敲一个字符触发一次全库事务，标签增删与计划块选择同路径。微信官方文档明确提示过多同步读写存储会显著影响耗时。 |
| P2（待确认） | 清空数据不覆盖本地界面偏好键 | `plan-and-record.todo-sort.v1`、`plan-and-record.project-collapse.v1`、`plan-and-record.recent-log-highlight` 绕过 `LocalRepository` 直接读写 `wx.storage`，而 `clearAllData` → `reset()` 只处理主库与升级前快照键，三个偏好键在“清空数据”后原样留存，与基线 5.4.3 的“删除全部用户数据”不符。`recent-log-highlight` 有 `localProfile` 校验，另两个没有，覆盖导入后会残留上一份资料库的项目 ID。折叠状态的失效清理只发生在页面内存（`plans/index.js` 的 `refresh`），`saveProjectCollapsedIds` 只在 toggle 处理器里调用，因此持久化值单向增长。2026-08-06 已确认 product-design 5.4.6 为正式方案，本行保留至代码按该节收敛为止。 |
| P2（待确认） | 失败回滚的缺失键判断与真机语义不符，测试替身掩盖了差异 | `restoreStoredValue` 以 `value === undefined` 判断“原本没有这个键”，但 `wx.getStorageSync` 对不存在的 key 返回空字符串而非 `undefined`（已核对微信官方文档），因此 `remove` 分支在真机上永不执行，一次失败的 `replace()` 会把空字符串写进升级前快照键。当前后果轻微，但迁移备份一旦按上面第二条实现，该判断即成为承重逻辑。同时 `MemoryStorageAdapter.get` 基于 `Map.get` 返回 `undefined`，所有回滚测试验证的都是生产不会走到的分支。仓库其实已知这个坑（`WxStorageAdapter.has()` 特意改用 `getStorageInfoSync().keys.includes()`），但认知没有传导到回滚路径与测试替身。建议修复后把该返回值语义补进 `AGENTS.md` 的常见坑点。 |
| P2（待确认） | 前台恢复计时无条件写库并推进根 `updatedAt` | `recoverTimer()` 的“继续运行”分支也在 `transaction` 内，只要有计时在跑，每次 `App.onShow` 都会全量重写资料库并推进根 `updatedAt`，即便没有任何变化。除叠加上面的写放大问题外，还有语义后果：`commitJsonImport` 用 `persistedValueEquals` 做 stale 检查且根 `updatedAt` 参与比较，用户在导入确认弹窗期间切出再切回，导入会被“本地数据已变化，请重新预览后再导入”挡掉，而他实际什么也没改。 |
| P2（待确认） | `develop` 环境 8 秒恢复窗口硬编码在启动流程 | `bootstrap.js` 的 `DEVELOPMENT_RECOVERY_TIMER_SPAN_MS` 只在 `envVersion === 'develop'` 生效，功能上安全，但代价是真实的 24 小时恢复路径在体验版和正式版从未被走过。需确认该调试开关是否保留，以及正式版恢复窗口的验收方式。 |
